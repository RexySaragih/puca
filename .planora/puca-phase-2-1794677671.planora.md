# Púca Phase 2 Fork-Pool Parallel Scoring

Plan profile: feature
Review status: in-review
Applicable domains: backend, data, api, integrations, security, operations
Problem: Speed the existing local Vitest pre-commit loop by scoring mutants across N isolated child Vitest keep-alives, without changing default `--workers 1` Phase 1 behavior or Phase 1 correctness locks.
Users: App developers opting into `--workers N` before commit; maintainers proving N=1 oracle identity and N=4 wall-clock vs Phase 1 on the in-repo fixture.
Scope: `--workers` flag; in-process VitestTestRunner when N=1; PooledVitestTestRunner when N>=2; coordinator reverse-map+baseline then close then fork N; parent NAPI discover/apply and NoCoverage; child RAM inject + runRelated; parent timeout kill; 512 MiB RSS recycle; crash RuntimeError; globalSetup+N>=2 exit 2; JSON sort by site.id; verbose recycle count. Spec: `.planora/puca-phase-2-technical-solution.md`.
Out of scope: V8 inspector coverage; disk cache; worker_threads isolation; npm prebuilds; Stryker/zod bake-off; TUI; puca.config.ts; @puca scope; new operators; A6/exclude/status changes.
Assumptions: Phase 1 A1–A12 stay; --workers omit=1; invalid --workers exit 2; WORKER_RSS_CAP_BYTES=512MiB; peak Vitest hosts max(1,N); Windows not a gate; setupFiles per child allowed; parent timer is Timeout source of truth.
Success criteria:
- SC-201: Given fixtures/loop, when `puca --workers 1 --mutate 'src/**/*.ts'` (fixture cwd), then statuses sorted by site.id equal the Phase 1 oracle and exit code matches.
- SC-202: Given the same fixture (or checked-in fixtures/loop-parallel if loop is too small), when `--workers 4` including warm pool, then wall-clock is <= Phase 1 sequential on that machine and sorted statuses equal N=1.
- SC-203: Given `--workers 0` or `--workers 1.5` or `--workers` without a value, when parse runs, then exit 2 and stderr names the flag.
- SC-204: Given a hung child mutant, when the parent outer timer fires, then that mutant is Timeout, only that child is killed, a replacement is spawned, the mutant is not retried, and other children continue.
- SC-205: Given a live child response with rssBytes above 512 MiB, when the parent handles it, then the mutant status is unchanged and the child is replaced before the next job on that slot.
- SC-206: Given a child crash or IPC disconnect mid-mutant, when the parent handles it, then status is RuntimeError with stderr message, child replaced, no retry, run exit 2.
- SC-207: Given vitest config globalSetup and `--workers 2`, when the session starts, then exit 2 before scoring forks and stderr tells the user to use `--workers 1`.
- SC-208: Given `--json` on N=1 and N=4, when mutants in each file are sorted by id, then the documents match.
- SC-209: Given a candidate with zero related specs, when scored, then all sites are NoCoverage and no IPC send occurs.
- SC-210: Given two in-flight mutants on two children, when each injects, then each child Map contains only its mutant (no shared parent overlay).
- SC-211: Given a `--workers 4` fixture run, when the workspace is walked, then no mutant sandbox dirs or mutated sources exist.
- SC-212: Given `puca` with no `--workers`, when createRuntime is inspected, then the test runner is VitestTestRunner and fork is not used.
Risks: R7 nested threads rejected; R8 globalSetup N-times refuse; R9 large IPC source accepted; R10 RSS recycle not Timeout; R1/R5 now per child.
Architecture decisions:
- ADR-013: child_process.fork pool, not worker_threads, not shared Map.
- ADR-014: Coordinator VitestTestRunner for map+baseline; close; then N scoring forks.
- ADR-015: process.send IPC; stdio not the protocol.
- ADR-016: workers===1 in-process Phase 1 path.
- ADR-017: globalSetup + workers>=2 exit 2.
- ADR-018: RSS cap via child rssBytes vs 512 MiB constant.
- ADR-019: Parent IPC timer assigns Timeout on child.kill.
Delivery strategy: Flag wiring → child IPC entry → pooled runner → use-case promise pool → JSON/verbose → fixture E2E.
Backend — Service boundaries: RunMutationSessionUseCase promise pool (N>=2); PooledVitestTestRunner owns forks; VitestTestRunner is one session (coordinator, N=1, and in-child). Runtime: parent + 0 children until green baseline, then N children. Failure: A6 unchanged; globalSetup refuse exit 2; hang kill one child Timeout no retry; crash RuntimeError no retry; RSS recycle not Timeout; no pool-wide respawn on N>=2.
Data — Entities: IPC request/response, per-child ActiveBuffer, SessionResult, MutationTestResult JSON. Identity: mutantId = site.id. Validation: workers integer >=1; rssBytes number. Relationships: child slot → at most one in-flight mutant. State: same five mutant statuses. Retention: IPC ephemeral; --json only extra disk write; no .puca/cache.json.
API — Consumers: human CLI; schema JSON consumers. Operations: existing flags plus `--workers <n>`. Inputs: cwd, workers, timeout. Outputs: UX-001/UX-002 terminal, exit 0/1/2, optional JSON sorted by site.id. Errors: bad workers and globalSetup refuse on stderr. Compatibility: unpublished; schemaVersion 2.
Integrations — child_process.fork of dist vitestChildMain.js; vitest/node from cwd in coordinator and children; Git/NAPI unchanged. Timeouts: parent per-IPC outer timer. Degradation: missing vitest/napi still exit 2; child death → RuntimeError continue.
Security — Trust: user tests execute in children on purpose. Controls: mutants never on disk; execArgv empty; kill one child; isUnderCwd; no shared overlay Map; no worker_threads isolation.
Operations — Node >=20.6; rust-toolchain; npm run build emits child js; --workers runtime flag; no publish/prebuild; Windows not a gate.
