# Púca Phase 3.3 Opt-In CI Gates and SARIF

Plan profile: feature
Review status: in-review
Applicable domains: backend, data, api, integrations, security, operations
Problem: CI buyers need opt-in mutation score and NoCoverage merge gates plus Survived SARIF annotations for PR Code Scanning, without changing the default zero-flag local Vitest pre-commit loop.
Users: CI/platform engineers wiring pipeline gates and SARIF upload; app developers who keep running bare puca; maintainers proving fixtures/loop non-regression.
Scope: --break-on-score (int 1..100), --fail-on-no-coverage, --sarif non-empty path; evaluateQualityGates + use-case exit authority; additive ReportPort.writeSarif + SarifFile; Survived-only SARIF 2.1.0; PRODUCT/ARCHITECTURE/AGENTS/README. Spec: `.planora/puca-phase-3-3-technical-solution.md`. Roadmap: `.planora/puca-phase-3-technical_proposal.md`.
Out of scope: HTML reporter; --report family; npm publish; optionalDependencies; @puca scope; cache; Jest; --workspace; magic default SARIF path; coupling --json thresholds to break-on-score; GHA pack/publish changes; ReportPort renames; weakening Survived to exit 1.
Assumptions: Phases 1–3.2 locks stay; score = Killed/(Killed+Survived)*100; denom 0 = N/A; exit 2 then 1 then 0 as ADR-032; no-flag path identical to 3.2.
Success criteria:
- SC-331: Given invalid --break-on-score, when parse/run starts, then exit 2 and stderr names the flag with the specified diagnostic family.
- SC-332: Given --break-on-score 80 and session score 75, when scored run completes without RuntimeError, then exit 1; RuntimeError still yields 2.
- SC-333: Given Killed+Survived=0 and --break-on-score 80, when scored, then score is N/A and exit is not forced to 1 by the score gate alone.
- SC-334: Given --fail-on-no-coverage and at least one NoCoverage, when scored, then exit 1; zero NoCoverage leaves other rules unchanged.
- SC-335: Given at least one Survived and score >= breakOnScore, when scored, then exit 1.
- SC-336: Given --sarif path, when scored with Survived mutants, then SARIF 2.1.0 is written with error results and line/col; omitting the flag writes no SARIF file; missing/empty path exits 2.
- SC-337: Given no-flag puca against fixtures/loop, when e2e runs, then statuses and exit match the Phase 3.2 baseline oracle contract.
- SC-338: Given package.json and workflows, when audited, then no HTML elements dependency, no npm publish/NPM_TOKEN, and no optionalDependencies in git.
Risks: R20 gate logic must not live only in CLI; R21 SARIF shape for GitHub; R22 no HTML dep creep; R11 no accidental publish.
Architecture decisions:
- ADR-031: Opt-in CI flags; default path unchanged.
- ADR-032: evaluateQualityGates + use-case exit authority; Survived never suppressed.
- ADR-033: Additive writeSarif + SarifFile; Survived-only; explicit --sarif path.
Delivery strategy: CLI parse/validate → gates in use case → SARIF port/adapter → E2E + docs.
Backend — Service boundaries: parseArgs refuse; RunMutationSessionUseCase sole scored exit authority; evaluateQualityGates pure. Runtime: same Vitest session. Failure: bad flags exit 2; gates exit 1; RuntimeError exit 2.
Data — Entities: SessionResult, optional sarif path string. Identity: site.id for SARIF messages. Validation: breakOnScore 1..100; sarif path non-empty. Retention: SARIF and --json are intentional writes; no cache.
API — Consumers: human CLI; GitHub Code Scanning (file upload by user CI). Operations: three new flags. Outputs: exit 0/1/2; optional SARIF; --json unchanged. Errors: flag diagnostics on stderr. Compatibility: unpublished; additive ReportPort only.
Integrations — No GitHub API client; SARIF file only. Timeouts unchanged. Degradation: missing path refuses before score.
Security — Trust: user tests execute on purpose; user-chosen SARIF path write. Controls: no mutant sources on disk; no default cwd SARIF surprise.
Operations — Document CI flag usage; no distribution workflow publish unlock; lint:deps and e2e remain gates.
